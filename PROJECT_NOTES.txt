------------------------------------------------------------------------------
1. WHAT THE ADDON IS
------------------------------------------------------------------------------
A minimal, centre-of-screen unit frame set for WoW: Forever. Each frame is a round
portrait with horizontal health (one side) and power (other side) bars. Frames exist
for PLAYER, TARGET, TARGETTARGET ("Target of Target", sized like focus), PET and FOCUS. Status
icons orbit the portrait; buffs and debuffs are drawn as a single row of icons above the bars.

It began as a replacement for "NotoriousR UI" (whose saved variables did not load
reliably) and grew into a full custom unit-frame addon.

Layout of one frame (player, default, not mirrored):

        [debuff icons ->  (growing left, over the health bar)]   [buff icons ->]
   [=== health bar ===(  portrait  )=== power bar ===]
            name             pips (secondary resource, player only)

 - Portrait: circular (mask texture), clickable. Left click = target, right click =
   unit menu ("togglemenu"). Works in combat (it is a secure unit button).
 - Health/power bars: NOT clickable. Health fills outward from the portrait.
 - "Mirror" swaps the sides (health on the right). Target, target of target and focus default to mirrored.

  Claude cannot run WoW, so code is syntax-checked and logic-tested only (see section 9).
- The user can supply TGA texture files for the artwork (see section 7).

Design preferences stated by the user (keep honouring these):
  * Everything about a frame (position, size, hide-Blizzard-frame, aura options...)
    is saved PER EDIT MODE LAYOUT. Any future per-frame option must also be per layout.
    (General-tab options are deliberately global.)
  * Frames are NOT movable from inside Edit Mode (for now); they move with /cr unlock.
  * Bars are never clickable. Portrait is clickable. Auras are never clickable.
  * Debuffs go over the HEALTH bar, buffs over the POWER bar, one single row each, allowed
    to run longer than the bar. Icon size scales with the frame (pet/focus/ToT are smaller).
  * Aura tooltips appear at the SAME location as the unit frame's own tooltip
    (anchored to the portrait, ANCHOR_RIGHT), not at the icon.
  * Aura timer text: placed ABOVE each icon; font size is locked to 40% of the icon size and the
    stack count to 40% (the Timer/Stack size sliders are commented out in Options.lua).
  * Aura timers must be at most 3 characters, in the form 45s / 79m / 12h / 5d (section 5).
  * Pet happiness: shown as a badge on the portrait edge (mood-coloured disc + Blizzard's happiness
    face), like the PvP flag. (The earlier "first buff slot" idea was dropped.)
  * Target of Target: works like the other frames, sized like focus/pet, driven by a 0.1s timer
    instead of unit events (the user prefers "timer only" over "events plus timer").
  * Be candid about what is unverified: Claude cannot run WoW. Say "untested" rather than asserting
    how the client behaves, and give the user a /run or /dump line to check when unsure.
  * Auras Blizzard does not display need not be shown (for now).
  * Aura WHITELIST/BLACKLIST is wanted LATER; the user has not decided the design yet.
  * NEXT planned feature: combat-entry glow and threat-change glow (user is deciding
    how they should look).

4. SAVED VARIABLES (CenterResourcesDB)
------------------------------------------------------------------------------
Initialised ONLY inside the ADDON_LOADED handler (Main.lua): create table, then
ns.CopyDefaults(ns.DEFAULTS, ns.DB) which fills missing/wrong-typed keys without touching
valid saved values. (The original problem with NotoriousR UI was loading/saving timing;
this pattern avoids it.) New options added in later versions are picked up automatically:
ns.Cfg() re-runs CopyDefaults on each per-layout table once per session.

CenterResourcesDB = {
  lastLayout = "Modern",           -- last Edit Mode layout name seen (used before PEW)
  general = {                      -- GLOBAL options
    locked, healthColor ("green"|"class"), barStyle ("smooth"|"flat"),
    textMode ("percent"|"value"|"both"|"none"), showRing, idleAlpha, combatAlpha,
    secondaryEnabled, secondarySize },
  units = { player|target|targettarget|pet|focus = <template> },  -- default template; seeds new layouts
  layouts = {                      -- PER EDIT MODE LAYOUT (key = layout name)
    ["Modern"] = { player = <cfg>, target = <cfg>, targettarget = <cfg>, pet = <cfg>, focus = <cfg> }, ... },
  layoutPos = {...},               -- legacy v2.1 positions; read once to migrate, then ignored
}

<cfg> (per frame, per layout):
  enabled, hideDefault (hide Blizzard's frame), scale, portraitSize, barLength, barHeight,
  barOverlap (% of portrait the bars tuck under the ring, default 4), showName (below the
  health bar), showIcons, mirror, pos = {x, y} (offset of portrait centre from screen
  centre, in UIParent units, scale-independent),
  auras = { enabled, maxCount (per row, default 10), sizeRatio (icon size as fraction of
            portrait size, default 0.4), spacing (px, default 2),
            altMethod (legacy flag, unused: the native path is always used),
            timerScale / countScale (stored but UNUSED: sizes are now locked at 40% of icon) },
  pet only: happiness = "auto" | "off" (the options panel only offers these two).

Defaults: player portrait 64, bars 190x18, pos (0,-190) | target 56, 170x16, mirrored,
name shown, pos (0,200) | targettarget scale 0.9, 40, 120x12, mirrored, name shown,
pos (440,200) | pet scale 0.5 (Core.lua default), 40, 120x12, pos (-440,-190) | focus scale 0.9,
40, 120x12, mirrored, name shown, pos (440,-190).

Edit Mode layout handling (Core.lua):
  - Active layout name from EditModeManagerFrame:GetActiveLayoutInfo(), falling back to
    C_EditMode.GetLayouts() (indexes 1/2 = Modern/Classic presets).
  - ns.UpdateLayoutKey() is called on PLAYER_ENTERING_WORLD and EDIT_MODE_LAYOUTS_UPDATED;
    if the layout changed, ns.Refresh() re-applies everything.
  - ns.Cfg(unit) returns the settings for the ACTIVE layout. A layout seen for the first
    time is seeded from the PREVIOUS layout's settings (or the template / v2.1 data).

5. FEATURES (what exists in v2.5.3)
------------------------------------------------------------------------------
Frames
  - Player, Target, Target of Target, Pet, Focus. All but the player use RegisterUnitWatch
    (show/hide with the unit even in combat). Each can be disabled, scaled, resized, mirrored,
    per layout.
  - TARGET OF TARGET (unit token "targettarget", secure button CenterResources_targettarget):
    built by the same CreateBlock code as the others; defaults = focus size, pos (440,200),
    mirrored; its own "ToT" tab in the options; overlay label "Target of Target - drag to move"
    (ns.UNIT_LABELS); Blizzard frame to hide = "TargetFrameToT" (NAME ASSUMED, not yet verified).
    It has NO unit-event registration. Main.lua runs a 0.1s C_Timer ticker that, while the frame
    is shown, calls UpdateColors/Health/Power/Portrait/Info/Icons. Auras are NOT in the ticker
    (a full aura update tears the container down and would flicker); they rely on the native
    container tracking "targettarget" plus the OnShow -> UpdateBlock refresh.
    UNVERIFIED: whether auras refresh when the ToT switches directly to another unit without
    the frame hiding; whether unit events fire for "targettarget" at all (user chose not to
    investigate; a possible check is
    /run local f=CreateFrame("Frame");f:RegisterUnitEvent("UNIT_HEALTH","targettarget");
    f:SetScript("OnEvent",function(_,e,u) print(e,u) end) ).
  - Bar text inside bars: percent / value / both / none (global).
  - Health colour: green or class/reaction colour (global). Portrait ring tinted by
    class/reaction colour. Dead/ghost -> portrait desaturated.
  - Player frame opacity: separate in-combat and out-of-combat values (global).
  - Bars tuck under the portrait ring by barOverlap % (so they do not show through a
    translucent portrait).
Status icons around the portrait
  - PvP pip (tinted Horde/Alliance/FFA), combat swords, resting "zZz" (player), group
    leader crown, raid marker, level number. Toggle with "Show status icons".
Secondary resource row (player only, below portrait)
  - Generic: shows pips for the class's secondary resource if the client reports one
    (combo points, holy power, soul shards, chi, arcane charges, essence). Hunter: none.
  - Pips are tiny StatusBars (secret-safe: SetMinMaxValues(i-1,i), SetValue(cur)).
Auras (buffs/debuffs) - NATIVE AURACONTAINER PATH (live in 2.5.3)
  - ns.UpdateAuras (UnitFrame.lua) ALWAYS uses the engine's widget: per block and per set
    ("debuffs", "buffs") it creates CreateFrame("AuraContainer", nil, b.root,
    "CustomAuraContainerTemplate"), calls AddAuraGroup(name, filter, {maxFrameCount, layout =
    {elementWidth/Height/Spacing...}, initializeFrame = MakeNativeAuraButton}), then SetUnit(unit),
    UpdateAllAuras(), SetFlowLayoutGrowthDirection(dirX, 1), and Show/Hide with UnitExists.
    Failures are pcall'd and printed with ns.Print. The old icon-by-icon code (set.icons,
    PositionIcon) is dead code now; set.icons stays empty. /cr auras reports container state.
  - Layout: debuffs over the health bar, buffs over the power bar, ONE row each, growing outward
    from the portrait side. Per layout options: show on/off, icon size (% of portrait), spacing,
    max icons per row. (Timer/stack text sliders are removed; sizes are locked at 40% of icon.)
  - MakeNativeAuraButton builds each button: Icon texture, a Cooldown frame (SetDurationCooldown)
    with swipe/edge/bling OFF, the countdown number drawn by the engine in a strip ABOVE the icon,
    an application-count FontString (SetApplicationCount), and a border texture coloured by
    SetDispelTypeTexture (harmful: debuff-type border, helpful: helpful border).
  - Tooltips and clicks on aura icons are handled by the engine (native buttons), not by addon
    scripts; the old tooltip code is dead. Right-click cancel: see the section below.
  - CONFIRMED by the user: auras display on custom frames with engine countdown text.

Level number, name and health colours (v2.5.6 rules; UpdateInfo, PickLevelColor, UpdateColors)
  - NAMES: always white on every frame.
  - LEVEL: player and pet always white. TARGET, TARGET OF TARGET and FOCUS share one rule set:
    UnitCanAttack("player", unit) (mob or unfriendly player) -> GetQuestDifficultyColor(level)
    ("??" level -> treated as player level + 10 = red); friendly player or UnitIsFriend NPC -> white;
    otherwise (unattackable, non-friendly NPC) -> UnitSelectionColor (the engine's orange).
    ASSUMPTION: players that cannot be attacked (e.g. unflagged other-faction) count as friendly -> white.
    Any secret/restricted value -> white (SafeColor pcall).
  - HEALTH BAR: target, targettarget, focus -> player-green if the unit is a same-faction player, else UnitSelectionColor(unit) (pcall'd, green fallback).
    Player and pet -> green (0.2,0.8,0.2). The old General option "Health bar colour" (green/class)
    was REMOVED from the options panel (db key general.healthColor is now unused). The portrait
    ring still uses class/reaction colour (UnitColor) when showRing is on.
  - Refresh: the 0.1s ticker in Main.lua refreshes UpdateInfo + UpdateColors for target and focus
    (and the full set for target of target). UNVERIFIED in game.

Hide Blizzard buff/debuff bars (General tab, GLOBAL option general.hideAuraBars, default off)
  - ns.ApplyAuraBars (called from ns.RefreshAll) hides BuffFrame, DebuffFrame and
    TemporaryEnchantFrame (whichever exist) with the same alpha-0 + huge hit-rect method as the unit
    frames (SetFrameHidden). Frame NAMES are assumed, not yet verified on Forever. Invisible icons
    might still react to the mouse; if so, consider Hide() instead.

Right-click to cancel your own buffs - WORKS via a built-in AuraButton method
  - AuraButton:SetCancelAuraButtons(buttons) (AuraButtonSharedMixin). The engine does the cancel
    itself, as with the built-in tooltip (SetTooltipAnchorPoint / SetHideTooltipInCombat also exist).
    Addon scripts still cannot run on the native buttons (Forbidden Partition); we only choose
    WHICH mouse button triggers the built-in behaviour.
  - The argument is validated like Button:RegisterForClicks. CONFIRMED IN GAME by the user:
    "RightButtonUp" and "RightButtonDown" are both accepted and cancel the aura.
    "RightButton" is REJECTED ("bad argument #2 ... usage: self:RegisterForClicks(buttons)").
  - Intended use (inside MakeNativeAuraButton, once per button, after _crNativeReady is set):
        if block and block.unit == "player" and not harmful and button.SetCancelAuraButtons then
            pcall(button.SetCancelAuraButtons, button, "RightButtonUp")
        end
    block.unit is the frame's unit token ("player"...), harmful is false for the buffs container.
    Only your own cancelable buffs can be cancelled, so it only makes sense on the player frame.
  - STATUS: IMPLEMENTED in the live UnitFrame.lua (MakeNativeAuraButton, after the Cooldown setup)
    using "RightButtonDown" (fires on press), exactly the guarded block above, and confirmed
    working by the user. Unverified: behaviour in combat.
  - DEBUGGING LESSON: Lua errors were invisible (the user's scriptErrors was off). Ask for
    /console scriptErrors 1 and /reload before diagnosing silent failures. A call that errors
    inside an engine callback (initializeFrame) stops the rest of the button setup, which showed
    up as "aura display wrong". Always pcall unverified widget methods.

Aura timer text (3 characters max: 45s / 79m / 12h / 5d)
  - The countdown number is the engine's Cooldown text. It is formatted by a shared
    NumericRuleFormatter (GetAuraTimeFormatter in UnitFrame.lua, above MakeNativeAuraButton),
    attached with cd:SetCountdownFormatter(fmt) inside MakeNativeAuraButton (pcall-guarded).
  - API facts (warcraft.wiki.gg, Midnight 12.0.5+, listed for Forever 1.60.1):
    C_StringUtil.CreateNumericRuleFormatter() -> formatter; formatter:SetBreakpoints({...}).
    Each breakpoint = { threshold (min input, in SECONDS), step, rounding (Enum.NumericRuleFormat
    Rounding: 0 Nearest, 1 Up, 2 Down), min, max, format (string with %d), components = { {div,
    mod, step, rounding} } }. Highest threshold <= value wins. formatter:FormatNumber(n) tests it.
  - Current rules: <=60s "%ds"; >60s up to 99m "%dm" (step 60 Up, div 60); >99m up to 99h "%dh";
    >99h "%dd". Constants MINUTES_FROM/HOURS_FROM/DAYS_FROM = boundary + 0.001 so the boundaries
    are exclusive. Everything rounds UP (just over 99m shows "2h").
  - REJECTED: Cooldown:SetCountdownAbbrevThreshold - it only switches between "1:31" style and
    abbreviated style; it cannot make the abbreviated text more detailed.
  - NOT YET CONFIRMED IN GAME: that the formatter shows 79m/12h/5d as intended (user changed the
    seconds rule to "%ds" and the timer font to 40% himself, so it was at least running).
Pet happiness (pet frame, v2.5; badge version)
  - API (CONFIRMED by user + other Forever addons): the classic global GetPetHappiness does
    NOT exist on Forever. Use C_PetInfo.GetPetHappiness() -> plain 1-3 (1 unhappy, 2 content,
    3 happy), then damage % and loyalty rate. Event: UNIT_HAPPINESS. The exact happiness
    number (Enum.PowerType.Happiness = 27, max ~1050) is a SECRET value via UnitPower, so only
    the three states are available. The user's /cr pet reported the icon texture as usable,
    and the happiness indicator was CONFIRMED WORKING by the user (2.6.0 test, same happiness code).
  - Mode "auto": a badge on the portrait edge (like the PvP flag): mood-coloured disc (Pip.tga)
    with Blizzard's happiness face (Interface\PetPaperDollFrame\UI-PetHappiness, texcoords per
    state, circle-masked) on top, plus a hover tooltip (state, damage %, loyalty). If the face
    texture is missing (checked with GetFileIDFromPath) only the coloured disc shows. "off" hides it.
  - Updated on UNIT_HAPPINESS, PET_UI_UPDATE, UNIT_PET and a 2-second ticker.
Hiding Blizzard's default frames (per layout, per unit)
  - PlayerFrame/TargetFrame/TargetFrameToT/PetFrame/FocusFrame: alpha 0 + huge SetHitRectInsets, plus a
    hooksecurefunc on SetAlpha to keep it at 0. No moving/re-parenting (avoids taint).
    Turning it off restores alpha 1 and the hit rect. Hiding the Blizzard target frame also
    hides the buffs it displays (ours replace them).
Moving frames
  - /cr unlock shows green boxes; drag any frame; /cr lock. Target/ToT/pet/focus show as
    previews while unlocked. Position saved per layout on drag stop.
Settings panel (/cr)
  - Tabs: General | Player | Target | ToT | Pet | Focus. Unit tabs have two pages: Frame / Auras.
  - Built with custom sliders/checkboxes/cycle buttons (right-click cycles backwards).
Combat handling
  - Protected frames cannot be resized/moved in combat. ns.Refresh() queues changes
    (ns.pendingRefresh) and applies them on PLAYER_REGEN_ENABLED. Alpha, bar values,
    icons and auras still update in combat.

8. CODE CONVENTIONS - KEEP FOLLOWING THESE
------------------------------------------------------------------------------
- SECRET VALUES: never do arithmetic, comparisons or string ops on UnitHealth/UnitPower/aura
  data. Pass them straight into StatusBar/FontString/Texture/Cooldown APIs. Use
  UnitHealthPercent/UnitPowerPercent with CurveConstants.ScaleTo100, AbbreviateLargeNumbers
  (all inside pcall). Wrap risky API calls in pcall; use ns.Safe for update functions.
- All settings reads for a frame go through ns.Cfg(unit) (per layout). Never read
  ns.DB.units[...] directly (that is only the template).
- Anything that touches the secure frames (SetSize, SetPoint, SetScale, Show/Hide,
  SetHitRectInsets, RegisterUnitWatch) must run out of combat: use ns.Refresh(), not
  ns.RefreshAll(), from option setters.
- Event registration is wrapped in pcall (unknown event names do not break loading).
- Saved variables are only touched after ADDON_LOADED.
- Options UI uses only plain frames/textures + a few safe built-in fonts: no Blizzard
  widget templates (they change between clients).
- Bump "## Version" in the .toc for every delivered build.
- When adding a per-frame option: add it to ns.DEFAULTS.units.* (all five units: player, target, targettarget, pet, focus),
  read it via ns.Cfg(), apply it in LayoutBlock / the relevant Update function, add a
  control in Options.lua (BuildUnitTab), and make sure existing saves pick it up
  (CopyDefaults does this automatically).

Update flow (UnitFrame.lua):
  ns.RefreshAll()  -> for each block: set bar textures, LayoutBlock, ApplyLock,
                      ApplyBlizzard, UpdateBlock
  ns.UpdateBlock() -> UpdateColors, UpdateHealth, UpdatePower, UpdatePortrait, UpdateInfo,
                      UpdateIcons, UpdateSecondary, UpdateHappiness, UpdateAuras
  Unit events (Main.lua) call the individual Update* functions for the matching block.
  (Target of target is the exception: no unit events, a 0.1s ticker instead - see section 5.)

Frame levels inside a block (root = secure button, size = portrait): bars +1,
secondary row +2, aura containers +2, portrait frame +3 (disc, portrait, ring), icon frame
+6, unlock overlay +8.

13. TEST HISTORY AND RESEARCH NOTES (read before touching auras or happiness)
------------------------------------------------------------------------------
What the user actually observed (this is the ground truth; research below is secondary):
  2.4.0  Target (and other) auras visible in AND out of combat.   -> original aura code WORKS.
  2.5.0  Auras still worked; pet happiness did NOT (it called the classic global GetPetHappiness,
         which does not exist on Forever).
  2.5.1  Happiness switched to C_PetInfo.GetPetHappiness (works; confirmed in the 2.6.0 test).
  2.6.0  Happiness worked, but auras stopped displaying on all custom frames. Cause: the new
         native AuraContainer path REPLACED the working code and drew nothing. Container creation
         reported success, so the old-code fallback never ran. Removed in 2.5.2.
  An early mistaken theory (that Forever blocks addon reads of hostile/combat auras) was NOT borne
  out for this addon's code path. Do not "fix" auras based on it.

  2.5.3  The user later switched ns.UpdateAuras to ALWAYS use the native container (comment in the
         code: "updated to always use the alt method") and it DISPLAYS auras with engine timers.
         So the 2.6.0 failure was a problem of that earlier implementation, not of the widget.
         The timer text then came out as "2h" (engine default abbreviation), which led to the
         custom NumericRuleFormatter (section 5). SetCountdownAbbrevThreshold was tried and
         rejected (it only toggles "1:31" style vs abbreviated).

Rules that follow from this:
  * Do not replace the working aura code without a fallback. The native container is now the
    live path: change it in small steps, keep pcall guards, and use /cr auras to diagnose.
  * Add happiness-like features as separate modules; test auras after each step.

Forever API facts (web research + user testing):
  * Pet happiness: the global GetPetHappiness does NOT exist. Use C_PetInfo.GetPetHappiness() ->
    plain 1-3 (1 unhappy, 2 content, 3 happy), then damage % and loyalty rate. Event
    UNIT_HAPPINESS. Exact value (Enum.PowerType.Happiness = 27, max ~1050) is a SECRET value.
    Icon texture Interface\PetPaperDollFrame\UI-PetHappiness exists in the client.
  * The client has a native aura widget (USED in 2.5.3): CreateFrame("AuraContainer", nil,
    parent, "CustomAuraContainerTemplate"); AddAuraGroup(key, "HELPFUL"|"HARMFUL", {maxFrameCount,
    initializeFrame}); SetUnit(unit); UpdateAuras via UpdateAllAuras(); layout via SetAuraGroupLayout
    ({elementWidth, elementHeight, elementSpacing}), SetFlowLayout* (values from AnchorUtil.FlowDirection,
    key names not confirmed). Other authors report it can draw auras even when addon reads are
    blocked, and that AddAuraGroup threw for Plater on Forever 1.60.1 with some option tables.
  * Cooldown countdown formatting: Cooldown:SetCountdownFormatter(NumericFormatter) exists since
    Midnight 12.0.5; formatters come from C_StringUtil.CreateNumericRuleFormatter (section 5).
    Cooldown:SetCountdownAbbrevThreshold exists but is not useful for this.
  * Unit events for "targettarget": UNKNOWN (not tested). Blizzard's own ToT frame has historically
    refreshed on a timer; hence the timer-only design.
  * Threat: EllesmereUI's "Forever Essentials" has a threat meter/borders on Forever, so some threat
    information is readable (verify before building the glows).
